# 飞书多维表格同步技术探索

日期：2026-10-14。范围：F01至F03的技术探索，尚未写程序、尚未连接真实飞书。

用户本轮要求是把任务面板的数据经飞书CLI上传到飞书多维表格的线上数据，并且**同一条记录的修改以最新时间为标准**。核实结论是：飞书官方提供CLI（`lark-cli`），多维表格的建表、字段、记录查询与批量增改都在其命令面内，本机只需Node.js即可安装；因此技术上可行，主要待定的是表结构、冲突粒度、删除传播和同步频率这些业务规则，以及若干需要实测的CLI行为。

## 1 已确认的使用规则

- 目的：任务先保存在本地，通过飞书多维表格与手机交换任务（PRD第3节、第11行）。飞书是"另一块屏幕"，不是新的数据源。
- R73：飞书设置记录连接配置与接入状态；实际双向同步后续开发。**任务编号、修改时间及阶段编号应稳定，为后续匹配同一任务提供基础**。
- R83：本轮只做界面与配置备份时的边界；现在要开发真实同步，属于F01至F03范围。
- 第15节：飞书双向同步需单独定义**任务与阶段字段映射、手机修改后的冲突处理、删除传播、离线合并与同步频率**。
- 用户本轮新增规则：**同一条记录的修改，以最新时间记录为标准**（即冲突时后改的覆盖先改的）。
- 手机修改任务**不自动启动电脑Codex**；远程执行需另行提出。
- PRD第19节：时间提醒与AI原因分别管理，不用一个字符串覆盖全部状态；飞书同步不得破坏这个区分。
- F02：同一编号的任务要合并，不能重复建行；F03：电脑新增、手机修改、双端冲突、断网恢复和删除都要有可重复的检查步骤。

## 4 表结构与字段映射

### 4.1 匹配键

- 任务匹配键用`WorkItem.Id`（Guid文本），写入一个文本列「任务编号」，比飞书自动编号（1005，会随行增加变化）更适合长期匹配。
- 阶段匹配键用阶段编号（0起连续），配合任务编号即为全局唯一。
- 与之配套：任务编号与阶段编号在本程序里已经稳定（R73），不需要改现有模型。

### 4.2 表结构三个候选（需要用户选择）

**方案A：一行一任务，阶段压成一段多行文本**

| 优势 | 缺点 |
| --- | --- |
| 表最简单，一眼看懂一整条任务 | 阶段用文本拼接表示，手机端改动可能破坏格式，解析失败就得兜底 |
| 读写量最小 | 手机无法结构化增删单个阶段；阶段级冲突只能整条决胜 |

**方案B：一行一任务，阶段用固定数量的列组（推荐）**

列组形如「阶段0名称/阶段0正文」……到「阶段5名称/阶段5正文」，另有一列「其余阶段」放超出的部分（只读展示）。

| 优势 | 缺点 |
| --- | --- |
| 单表；手机端编辑单个阶段就是改单元格，最自然 | 列较多（约12至14列），首次需要建列（可由程序自动建） |
| 无格式解析风险，字段级映射清晰 | 手机端若跳着填写阶段（如只填阶段2），拉取时需要把空阶段压缩后重排编号 |
| 与本地阶段模型可直接对照 | 超过6个阶段的正文不能在手机上单独编辑 |

**方案C：两张表（任务表 + 阶段表，用关联字段相连）**

| 优势 | 缺点 |
| --- | --- |
| 与本地模型1:1对应，粒度最细，手机可任意增删阶段 | 需要两张表、两次写入；父记录先建才能建子记录，写入顺序有依赖 |
| 阶段级冲突可以在阶段粒度上裁决 | 同步代码量与出错面明显更大；手机端建阶段要自己填关联 |

推荐**方案B**：一份表、手机端可读可改、没有格式解析风险，代价是列数多且阶段数有实际上限（超出部分只读展示）。若手机端必须能自由增删阶段，再升级到方案C。

### 4.3 字段映射（以方案B为例）

| 本地 | 飞书列名 | 列类型 | 写入值 | 读回形态 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `WorkItem.Id` | 任务编号 | 文本(1) | `"d3f1…"` | `[{text,type}]` | 匹配键，程序只读不给人改 |
| `Title` | 标题 | 文本(1) | 字符串 | 同上 | 空标题可就地让人补写 |

| `Stages[i].Text` | 阶段i正文 | 文本(1) | 字符串 | 同上 | 多行文本 |

选项类字段（AI、优先级、当前状态）的注意点：飞书单选/多选的选项必须在字段里先存在，写入不存在的选项会失败；而本地用户可以随时改名或删除选项。这一点需要一个明确规则，见第8节选择项6。

## 5 同步规则设计

### 5.1 变更检测：同步台账

同步台账保存"上次同步时两端的样子"，是判断谁改过的依据，建议独立成`feishu-sync.json`放在数据目录（与`board.json`同级，原子写入）：

```
每条任务：任务编号 → { record_id, 上次同步的本地内容摘要, 上次同步的云端内容摘要,
                       上次同步的本地时间, 上次同步的云端修改时间 }
全局：     { 表格标识, 字段映射快照, 上次同步结果, 云端与本地的时钟偏移, 待清理的墓碑 }
```

用"内容摘要"而不是只比时间的原因：本地时间与云端时间是两台机器的时钟，不能直接比大小；而"内容有没有变"是确定的。这也是绕开`Submit`无条件刷新时间戳的办法。

### 5.2 冲突裁决（用户规则：以最新时间为标准）

**规则一：直接比绝对时间。** 拿本地`UpdatedUtc`与飞书系统列1002比较，新的胜。
- 优点：最直白，符合用户说法。
- 缺点：两台时钟不同源，本机时间不准就会判错；"打开编辑窗口点一次保存"也会刷新本地时间而错误胜出。

**规则二：先看谁改过，两边都改过才比时间（推荐）。** 每次同步按台账判断：
1. 只有本地变 → 上传覆盖云端；
2. 只有云端变 → 下载覆盖本地；
3. 两边都变 → 比较修改时间，最新者胜（即用户规则）；
4. 都没变 → 跳过。

比较时间时用同步时测得的"云端时间与本机时间的偏移"把云端时间换算到本地时间轴，避免时钟偏差误判。这样既保留"以最新时间为标准"，又不会被无改动的保存或时钟漂移搅乱，代价是多存一份内容摘要。

**规则三：逐字段裁决。** 每个字段各比各的时间，能同时保住两端的部分修改。
- 缺点：飞书系统字段是**整条记录**粒度，拿不到字段级修改时间；要做就得给每个字段再加一列"修改时间"，列数翻倍、代码复杂度大幅上升。
- 结论：不建议第一版做，除非实测出"两端经常各改不同字段"确实很常见。

推荐规则二。

### 5.3 删除传播

本地`Delete`目前直接从列表移除、不留痕迹；云端删除则会让记录消失。两边都不可靠，建议：

- **在飞书表加「已删除」复选框做软删除**：本地删除后不是删行，而是把该行打勾；手机上也能用这一列删除任务；程序拉取到已删除打勾的行，就把本地任务移除。
- 本地删除的检测：同步层订阅`BoardEngine.Changed`，对比台账发现某个任务编号不在本地了，就用当时时间记一条"本地删除时间"。时间戳用于和手机端修改做冲突裁决。
- 台账丢失时的兜底：云端有某任务编号而本地没有 → 按"本地已删除"处理（软删除打勾）。反过来若台账与云端都空，就按新增处理。
- 不推荐物理删除：`+record-delete`可能是高风险命令（待实测），删掉不可恢复，且手机端误删无从挽回。
- 代价：表里会积累已删除的行，占用20000行上限；可以提供"清理已删除行"的手工按钮（这一步才需要高风险确认）。

### 5.4 触发、频率与离线

- 建议默认：设置页手动「立即同步」按钮 + 程序启动时自动同步一次（可关）。定时轮询默认关闭，需要时再开（间隔如5分钟，需实测空闲开销）。
- 写入必须串行、单批≤200条，批次之间留间隔；不能并发写同一张表。
- 幂等：上传前先用`+record-list`/`+record-search`按任务编号查已有记录；查到就更新、查不到才新建。这样即使台账丢失或上次中断，也不会重复建行（F02要求）。
- 中断与断网：只有一批真正成功后才落盘台账；失败保留原台账，下次重试。禁止"先改台账后写云端"。
- 写入成功不立即回读（异步链路），需要验收时本轮全部改完再统一读。

### 5.5 异常规则

| 情况 | 处理 |
| --- | --- |
| CLI未安装 | 显示未接入，给出安装说明；不虚报已连接（A16） |
| 未登录或凭证过期 | `auth status --verify`判为未连接，引导重新授权 |
| 权限不足 | 读取错误里的`missing_scopes`精确补权限，不顺手申请多余权限 |
| 表格链接无效 | `+url-resolve`失败即明确提示，不静默改成别的表 |
| 缺少列 | 连接时核对字段清单，列出缺哪些列并提供按类型自动建列 |
| 列类型不符 | 错误码`1254015`，提示具体是哪一列 |
| 选项不存在 | 单个选项写入失败时保留该列原值并提示，其余字段照常写入 |
| 并发写冲突`1254291` | 串行化并退避重试，不并行写 |
| 单表超过20000行 | 停止新增并提示，不静默丢弃 |
| 退出码10（高风险确认） | 展示动作与参数，用户明确同意后才追加确认参数重试；**绝不静默重试** |
| 云端记录被删 | 按5.3规则传播到本地 |
| 时钟偏差过大 | 同步时测量偏移并提示；偏差过大时本次不做时间裁决，改为人工确认 |
| 列被改名 | 用`field_id`写入；名称变化时刷新映射快照 |
| 写入成功但读回未更新 | 视为成功，不在同一轮反复回读 |
| 部分批次失败 | 台账只落成功批次，下次继续，不重复创建 |

## 6 候选技术路线

### A 桌面程序调用官方CLI可执行文件（推荐）

由面板以子进程方式调用`lark-cli`，用argv数组传参、`--format json`读结果、按`ok`字段与退出码判成败。数据经stdin或工作目录下的临时文件传递。

优势：直接复用官方实现的认证、分页、限流、错误分类与审批门禁；命令面覆盖建表建列与记录增改；升级CLI即获得修复；程序本身不接触凭证与令牌。缺点：多一个外部依赖（需Node或已安装的CLI）；输出契约需按`ok`解析；跨进程调用要处理编码、超时与取消。

### B 官方CLI + 内嵌Go扩展（重投入）

官方支持把CLI作为库内嵌：写Go包实现`Credential`/`Transport`/`Restrict`/`Observer`/`Wrap`/`On`扩展点，在wrapper `main`里导入后重新编译，即可自定义凭证来源、审计所有请求、限定命令范围。[内嵌文档](https://open.larkoffice.com/document/mcp_open_tools/feishu-cli/embed-feishu-cli-in-agent)

优势：可统一凭证、审计与命令白名单，最适合企业内嵌。缺点：需要Go工具链与自行维护的构建产物，对一个.NET便携程序属于重投入；本项目是个人单机使用，收益不明显。结论：暂不采用，仅作为将来要做"集中凭证/审计"时的备选。

### C 程序内直接调用HTTP接口

用.NET的`HttpClient`直接调`open-apis/bitable/v1`，不依赖CLI。

优势：无外部依赖、单进程、可控性最好；接口本身能力等价（批量增改500条、查询500条/页）。缺点：要自己实现令牌获取与刷新、分页、限流退避、错误码分类；凭证要由程序保存与保护，安全责任从OS密钥链转移到本程序；失去CLI的`--dry-run`预览与高危确认门禁；与R69"只有真实验证成功才显示已连接"相比，验证路径更长。

### D 第三方CLI

社区工具`feishu-cli`（[riba2534/feishu-cli](https://github.com/riba2534/feishu-cli)）覆盖base/v3与bitable/v1全域，含附件、视图、仪表盘、表单、高级权限与工作流。

优势：覆盖更细。缺点：非官方、维护与安全由第三方决定、接口与输出契约随时可能变。结论：不作首选。

### E 手工导出再上传（兜底）

程序导出CSV/JSON，由用户自己粘进多维表格。

优势：零依赖、立刻能用、不涉及凭证。缺点：不是同步，双向冲突与删除传播都无从谈起，手机改动也回不来。结论：只作为CLI路线全部失败时的降级方案，或作为"先看到数据长什么样"的临时手段。

## 7 实施建议和验收

建议顺序：

1. 安装并只读验证（不写任何数据）：安装CLI → `config init` → `auth login` → `auth status --verify` → `base +url-resolve`解析用户提供的**测试表** → `+field-list`读列 → `+record-list`读记录。同时实测第3节列出的待测项。
2. 单向上传：建列与全量建记录 → 增量更新 → 软删除标记。台账与幂等匹配在这阶段建立。
3. 拉取与冲突：按规则二实现变更检测与时间裁决，接云端删除。
4. 界面：飞书分区显示真实状态（未配置/连接中/失败/已连接），提供表格链接、连通性验证、立即同步与同步结果。
5. 回写文档：PRD第11、15节，TASKS.md的F01至F03，IMPLEMENTATION.md与INDEX.md。

测试策略（与现有工程一致）：把字段映射、变更检测、冲突裁决、删除传播写成纯规则代码放在`Taskboard.Core`，用`tests/Taskboard.Checks`的隔离目录方式验证（假CLI返回构造好的云端记录，不需要真实账号）；真实链路只用一张**测试多维表格**手工验收，绝不碰正式任务数据。

| 隔离验证 | 应看到的结果 |
| --- | --- |
| 电脑新增任务后同步 | 云端出现一行，任务编号与本地区分唯一 |
| 电脑再改同一任务后同步 | 同一行的列被更新，行数不增加（F02不重复） |
| 手机改「当前状态」后同步 | 本地任务移到对应列表，其他字段不受影响 |

| 断网或CLI失败后重试 | 台账不变、云端不出现重复行，恢复后接上 |

## 8 需要用户确认的选择

| 编号 | 选择 | 推荐及效果 |
| --- | --- | --- |
| 1 | 同步方向范围：只上传，或上传+拉取 | 推荐先做上传打通链路，再做拉取；冲突规则在拉取阶段才真正生效 |
| 2 | 表结构：方案A/B/C | 推荐B（单表、阶段列组），手机可读可改且无格式解析风险 |
| 3 | 冲突粒度：规则一/二/三 | 推荐规则二（先判断谁改过，两边都改才比时间），最稳且仍符合"最新时间为准" |
| 4 | 删除传播：软删除复选框或物理删除 | 推荐软删除，误删可恢复；代价是表内保留已删除行 |
| 5 | 同步触发：手动/启动时/定时 | 推荐手动+启动时一次，默认不定时轮询 |
| 6 | 选项改名与删除的处理：以本地为准自动加选项，或只同步两边都有的选项 | 前者顺手但会在飞书侧堆积选项；后者更保守但改名的选项同步不过去 |
| 7 | 超过6个阶段的处理：只读拼接展示，或改用方案C | 推荐先只读拼接；阶段普遍超过6个再考虑两张表 |
| 8 | CLI获取方式：用户自行安装、程序检测缺失后引导安装，或便携包内置CLI | 内置最省事但需随包分发第三方二进制并做版本管理；引导安装最轻 |
| 9 | 是否现在安装`lark-cli`做真实探测 | 安装需要npm全局安装，并需要一次飞书扫码授权与一个自建应用，属机器级改动，需用户同意 |

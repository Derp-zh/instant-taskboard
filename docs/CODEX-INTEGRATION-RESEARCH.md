# Codex会话关联和任务自动流转技术探索

日期：2026-10-13；实测补充：2026-10-14。范围：C01至C04技术探索，独立模块已验证，正式面板尚未接入。

独立模块已通过真实临时会话验证执行结束、等待输入、恢复执行及权限请求，任务关联与双向移列具备可行基础。当前桌面会话的旁路实时状态仍未接通。Windows通知可以提供音频提醒，但不能单独承担准确会话关联和自动移列。具体证据见 [模块实测结果](CODEX-PROBE-RESULTS.md)。

## 1 已确认的使用规则

- 以PRD原有的会话关联、执行监听及自动流转为主，音频提醒为补充。
- 优先当前Codex桌面端，终端会话也兼容；任务由用户手动关联到准确会话。
- 只有“进行中”和“待操作”参与自动状态识别和相互移动。灵感库、完善中、暂搁置、已完成保留人工归类。
- Codex需要用户回答、批准权限等介入时进入待操作；实际恢复执行后回到进行中。问题与权限采用同一流转规则。
- 执行正常结束表示结果待检查，进入待操作，不自动标记业务任务已完成。失败、取消和失去监听仍分别记录原因。

若同一任务同时有时间提醒和AI待处理原因，关联Codex恢复运行后立即回进行中；时间提醒在任务卡片右上角保留红色小点，用户对该任务进行任何主动操作后清除。后台刷新和AI状态变化不清除红点。音频种类、催促频率、勿扰策略和多会话聚合规则仍为后续选择。

## 2 现有工程的接入位置

PRD R53、R67、R69至R72、R76和A18，以及重写思路第12节，要求区分AI标签、平台连接、会话关联和执行记录。当前源码仍明确显示未接入，不能把配置备注或AI标签视为监听成功。

当前`WorkItem`有稳定任务编号和`PendingReasons`，`Preferences.ConnectionConfigs`保存接入配置备注；`BoardState.Sessions`实际是任务编辑草稿，不能用它存Codex会话。`BoardEngine.Merge`已按用户改动字段合并编辑，并保留后台待处理原因，适合延续到AI事件。配置备份不含任务内容，因此任务到会话的关联与监听游标应属于业务数据，不能塞进配置备注后跟随配置备份导出。

建议增加独立的关联、执行快照和事件处理记录，由接入层送出标准事件，任务规则决定是否移列，界面只刷新受影响卡片。数据字段需兼容已有文件；时间原因与AI原因分别管理，不用单个字符串覆盖全部状态。

## 3 Codex能力和本机证据

官方App Server协议提供会话读取、轮次历史和运行事件；包含完成事件、提问及多类审批请求。需要连接到实际运行目标会话的服务，另起服务读取历史不等于监听原执行。[OpenAI App Server文档](https://learn.chatgpt.com/docs/app-server)

本机安装的CLI为`0.162.0-alpha.17.2`。通过该程序导出协议，确认以下能力：

| 字段或事件 | 本次用途 |
| --- | --- |
| `thread.id` | 绑定准确会话 |
| `thread.sessionId` | 会话树分组；不能替代准确会话编号 |
| `thread/status/changed`、`ThreadStatus` | 运行、空闲、未加载、系统异常 |
| `waitingOnUserInput`、`waitingOnApproval` | 待回答、待批准 |
| `turn/started`、`turn/completed` | 本轮开始和终止；完成状态区分completed、failed、interrupted |
| `item/tool/requestUserInput` | 结构化提问 |
| `item/commandExecution/requestApproval`、`item/fileChange/requestApproval`、`item/permissions/requestApproval` | 命令、文件或权限审批 |
| `serverRequest/resolved` | 某个请求已清除；不单独证明AI已恢复执行 |
| `thread/read`、`thread/turns/list` | 校验关联、获取快照、重连补查 |

本机协议中`thread.id`与`sessionId`含义不同，分叉或子会话可能共享会话树编号。关联必须保存准确的`thread.id`，否则容易把多个会话的状态串到同一任务。子Agent结束也不代表主会话结束。

命令帮助有`codex agents`、`codex app-server proxy`与共享daemon管理入口。但本轮`daemon version`未能连接默认控制套接字，报Windows错误10050；默认路径检查也未找到套接字。该结果只说明这一入口没有接通，不能认定所有CLI路线不可行。没有停止、重启、迁移现有Codex服务或会话。

本机协议没有独立`thread/subscribe`方法。`thread/read`可以只读；`thread/resume`有重新加入运行会话的语义，但不是纯元数据读取，需要验证订阅是否改变原桌面端的提问、权限路由或线程配置。不能把监听器变成第二个自动审批客户端。

## 4 手动关联的设计

建议用户流程：任务编辑或卡片菜单 → 关联Codex会话 → 选择真实会话或粘贴编号 → 核对标题、项目目录、来源和状态 → 确认关联。

列表应从可信服务或已验证的本地历史索引读取，并包含桌面端实际使用的来源类型，不能只依赖默认终端筛选。重名标题和同一项目内的多个会话靠编号区分，不用最新会话、进程名称、窗口标题或项目目录自动猜测。

建议第一阶段一项任务有一个当前有效的Codex会话；同一个会话不同时绑定多个任务。更换时关闭旧关联的生效资格、保留历史，记录新的绑定代次。此为降低串任务风险的方案，尚未定稿；未来多AI、多会话需要另定聚合规则。

关联记录建议含：任务编号、平台、服务来源、本机用户配置范围、`thread.id`、关联时间、绑定代次、有效状态及上次已处理轮次。`sessionId`仅作辅助分组。认证令牌与连接端点分开处理，不复制原应用私有凭证。

关联时如果会话正执行，应接住当前轮次；如果已经空闲，以当时状态作基线，避免历史结束事件将任务突然移列。当前已等待回答或批准时可呈现该状态，是否补播一次音频可另选。关联展示“历史可读”和“实时监听有效”两种能力，不能只因编号能查到就显示绿色已监听。

会话分叉、换项目或用户换到另一个聊天不自动改绑。直接跳回准确聊天的入口需核实原应用支持的打开方式，不能编造深链接。第一阶段可显示会话标题、编号和来源帮助用户在原客户端定位。

## 5 自动流转和异常规则

以下只适用于任务当前在进行中或待操作；其他四列不会因后台事件被拉回。

| 真实信号 | 执行状态和处理 |
| --- | --- |
| 本轮运行且无待用户处理请求 | 进行中 |
| 等待回答 | 待操作，注明待回答 |
| 等待审批或权限 | 待操作，注明待批准 |
| 用户处理后AI实际恢复运行 | 清除对应AI等待原因，回进行中；时间提醒红点保留至用户主动操作该任务 |
| 本轮completed | 待操作，注明结果待检查；不设为已完成 |
| 本轮failed或interrupted | 分别记录失败/取消，提示检查；建议处于待操作，此异常移列细节待定 |
| 连接断开、线程notLoaded、读取失败 | 状态待确认，不按成功结束移列；保留已知状态和原因 |
| 查询到idle但没有准确轮次结果 | 不猜测完成；补查关联轮次结果 |

同时存在多个问题或审批时，一个请求已解决不应清掉其他请求。以等待标志和真实运行信号确认恢复，不能仅靠按钮点击、发送回复或`serverRequest/resolved`。若原客户端设置自动审批，审批事件发生也不一定代表用户仍需介入。

“一轮回复结束”与“整个业务任务完成”分开。普通文字问句未必触发结构化等待输入；该边界必须用真实桌面提问验证，不能用文本问号判断。长目标或多轮执行也可能出现多次轮次结束，需按用户要检查的执行单元确认提示频率。

事件归一化后建议记录平台、来源、会话编号、轮次编号、请求或事件编号、绑定代次和来源游标。重复、旧关联及旧轮次事件不再次响铃或移列。没有可靠事件编号时，用经过验证的状态迁移序号去重，而不是凭正文拼出“全局唯一ID”。

用户手动拖入其他四列表示退出自动流转范围；继续记录会话状态但不自动拉回。用户处理通知不等于人工完成任务，清除AI原因不能清掉时间提醒红点。红点作为单独的提醒未读标记保存，用户主动点击、编辑或移动等操作清除，周期提醒配置不因此停用。多个窗口编辑时按现有合并边界提交用户修改字段，保留最新后台状态。

## 6 候选技术路线

### A 接入同一个App Server

首选路线：本地适配器接入原桌面会话所在服务，先用只读状态快照验证准确性，再验证不影响原客户端的事件订阅。可先采用每1至2秒只查关联会话的轻量快照，后续接事件流；轮次历史用于补查结果。间隔是设计建议，需测延迟与空闲开销。

优势是能支持准确关联、等待与恢复，以及失败/中断区分。当前障碍是现有桌面服务入口和多客户端行为尚未验证。只有同一实际服务的数据才可用于实时判断；另起服务看到notLoaded不能当作原会话已停止。

重连后按游标补查，并重新读取当前状态：先纠正当前卡片，历史经过的等待状态不逐条补播音频。若历史已不足以补齐，显示状态待确认；不能用重连成功掩盖缺口。订阅与业务保存之间应保持可恢复的提交边界，重启后重放不会产生重复提示。

### B Codex原生回调转发

`notify`当前只回调`agent-turn-complete`，含会话及轮次标识，适合结束事件；不能独立覆盖提问、审批与恢复。[OpenAI通知配置](https://learn.chatgpt.com/docs/config-file/config-advanced#notifications)

Hooks支持生命周期和工具回调，非托管Hook需先经Codex信任审核；桌面会话适用性需要实测。[OpenAI Hooks文档](https://learn.chatgpt.com/docs/hooks)

可将回调事件快速写入本地队列，再由面板处理，保留原桌面或终端使用方式。缺点是Stop未必代表最终停止，PermissionRequest也可能被自动审核处理；工具提问、回答后恢复及准确会话编号必须验证。只在回调能证明具体状态时驱动移列，未覆盖状态显示未知。

回调仅转发，不返回审批决定、阻止执行或追加AI指令。不要为了测试Hook绕过Codex的信任机制。子Agent回调若使用父会话编号，需要验证归属，只能作为主任务辅助信息，不能直接标记主执行结束。

### C 已验证的本地执行记录

当原生服务无法接入，可探索只读跟踪本地会话文件或历史存储，按准确编号和轮次读取增量记录。需要确认当前版本的存储格式、分页历史、落盘时机及事件覆盖；不能假设旧JSONL格式仍完整可用。它适合部分补查，不能仅凭文件停止增长或进程退出认定成功。

此路线耦合版本较深，通常不如原生协议稳定；尤其权限与问题事件未必完整持久化，应先验证再承诺功能。读取范围限已关联会话，默认不抓取或保存AI正文。

### D 自有服务承载执行

如果当前桌面端无法旁路接入，另一个完整方案是让用户经共享服务启动终端Codex，面板连接同一服务。对面板自己承载的会话，协议和编号可控。但会改变启动方式，属于重要产品选择；不能未经确认把用户现有桌面会话改成面板发起执行，也不能承诺桌面端能随意改连服务。

### E Windows通知补充

Windows官方`UserNotificationListener`可以读取发送应用和通知文字，需要能力声明与用户授权。目标应用原声音关闭、通知保留后，可由面板播放自选音频。[Microsoft通知监听](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/notification-listener)、[按应用设置声音](https://support.microsoft.com/en-us/windows/experience/notifications-and-do-not-disturb-in-windows)

通知通常不能保证带有准确会话及轮次编号，也不表达“用户已处理、AI恢复执行”。因此它只做声音兜底，不能完整替代C02至C04，未知来源通知不驱动任务移列。

当前便携面板没有所需包身份配置。可验证单独安装带包身份的通知助手，再与便携面板通信；每台电脑需注册及授权。[Microsoft应用能力说明](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/app-capability-declarations)

本机安装应用显示名为ChatGPT，开始菜单身份是`OpenAI.Codex_2p2nqsd0c76g0!App`。实际通知发送身份仍需捕获核实，不只匹配Codex字样。应用不发系统通知时无从捕获，终端BEL也不等于Windows通知。勿扰、前后台、通知更新与两个来源重复响铃需实测。桌面通知有完成、问题和权限相关控制，仍受用户及系统设置影响。[OpenAI桌面通知说明](https://learn.chatgpt.com/docs/notifications)

## 7 实施建议和验收

建议顺序：验证A的服务入口与只读快照 → 验证等待/恢复和订阅不干扰原客户端 → 实现准确关联与事件记录 → 按已确认规则接自动流转 → 音频提醒 → A不满足的能力评估B或C。E可以补充声音，但不降低自动流转的数据准确性要求。

| 隔离验证 | 应看到的结果 |
| --- | --- |
| 两任务关联两个同项目、可重名会话 | 无串状态；不同thread.id准确区分，分叉不自动改绑 |
| 运行中关联与空闲后关联 | 当前执行能接住，历史结果不突然触发移列 |
| 提问及审批 | 进行中进入待操作，原因准确；原桌面仍正常处理请求 |
| 回答、允许、拒绝及多请求 | 只有真实恢复才回进行中；失败/拒绝不会误报继续执行 |
| 本轮完成、失败、中断 | 分别呈现，不自动标记已完成 |
| 断线、关闭会话和重连 | 断开不误报结束，重连补查且不重复响铃或移列 |
| 四个保护列、手动移动和更换关联 | 后台不拉回保护列，旧关联事件不生效 |
| 编辑未提交和时间提醒 | 后台变化不被旧草稿覆盖，多个原因分别保留 |
| 重启及数据写入失败 | 关联和游标可恢复，事件重放幂等，不操作正式数据 |
